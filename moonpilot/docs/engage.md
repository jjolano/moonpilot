# Lateral-only engagement
`moonpilot/engage.py` is the fork's half-engaged state: openpilot steers from the car's cruise **main switch**, and the car's own ACC takes over speed only once the driver sets it. It cannot be done on the openpilot side alone — panda blocks steering unless its own `controls_allowed` is true, and that flag is only set on the rising edge of stock ACC — so this is the fork's one feature that reaches into `opendbc` and `panda` as well as the openpilot tree. Read the whole chain before changing any part of it.

The permission itself is in the forked safety layer, `opendbc/safety/moonpilot/lateral_engage.h`, reached through `opendbc/safety/lateral.h`:

- **`controls_allowed` keeps upstream's exact meaning** — stock ACC engagement — and stays the only thing `get_longitudinal_allowed()` reads, so every longitudinal check, the brake/gas/regen exits and the heartbeat logic behave exactly as upstream wrote them. `controls_allowed_lateral` is a second, additive flag that only ever gates steering: all 12 reads of `controls_allowed` in `lateral.h` become `(controls_allowed || controls_allowed_lateral)`. A change that widens the first flag instead of the second hands the fork the longitudinal controls it does not have.
- **What arms it, where the brand decodes the switch (ARM_SWITCH):** the rising edge of the cruise main switch, or of the openpilot heartbeat while the switch is already on, and only when the brand's safety param enabled the rule. The heartbeat deliberately does *not* have to be true to arm, because it is a host message on pandad's 10 Hz USB heartbeat and openpilot can only set it a tick after it engaged — while it is already commanding torque. One frame this layer rejects resets `desired_torque_last = 0` in `steer_torque_cmd_checks`, and the upward limit is then `MAX_RATE_UP` measured from zero, so the limiter blocks every later frame until the command comes home (measured: after a single rejection a 15 unit/frame ramp is rejected in full). In the recorded failure that cost the car 0.92 s of `STEERING_LKA` on a torque-steered Toyota, which its lane-keeping ECU reads as a message dropout — `LKA_STATE` 9 → 11 → 3, and 3 is in `PERM_STEER_FAULTS`. What clears it: the arm's own signal going away — the switch, or a heartbeat older than `HEARTBEAT_GRACE_US` (300 ms, 3x pandad's heartbeat period, so a merely late bit cannot drop a live engagement) — `steering_disengage` for as long as it is asserted, a disable event in selfdrived, and the lag/validity path in `safety_tick` (both `controls_allowed = false` sites call `lateral_engage_exit()`). The `steering_disengage` term is **live only on Tesla**: it is upstream's own signal and only Tesla's rx hook sets it (`opendbc/safety/modes/tesla.h`), so on every other armed brand a driver's torque is handled the way upstream handles it — the car blends, and openpilot overrides rather than disengaging. `lateral_engage_common.py` injects the flag to hold the rule itself on the brands that never raise it, and its docstring says so, because a test that read as proof of a live disarm would be wrong.
- **Where a brand decodes no main switch, openpilot's own engaged heartbeat arms it (ARM_HOST), and that is what took the feature from four cars to every brand openpilot drives.** It is level-armed — the permission rises again on any fresh heartbeat — so a drop, a stale heartbeat or the lag exit, recovers by itself instead of waiting for a car signal to transition. The trust is the point and is taken deliberately, recorded in the rule's own header: on those brands the car corroborates nothing, and the permission rests on openpilot's claim that it is engaged, exactly as sunnypilot's MADS rests on `heartbeat_engaged_mads`. What keeps that honest is everything else in the layer: upstream drops `controls_allowed` after three mismatched heartbeats, `ActuatorGate` stops the command the moment `PandaState.controlsAllowedLateral` is not set, and the steering-override term is held on the *level* rather than an edge, so while Tesla's `steering_disengage` is asserted — Tesla is the one brand the fork arms that sets it — the permission stays down instead of returning on the next heartbeat with the driver still holding the wheel.
- **Brake, gas and cancel deliberately do not appear in the rule.** Keeping steering through a brake tap is the point of the feature, so the fork suppresses three events instead — `pcmDisable`, which is level-triggered whenever stock ACC is off; `pedalPressed`, the brake/gas disengage; and `buttonCancel`, which upstream raises on any `ButtonType.cancel` press for every brand but Hyundai (`car_events.py`). Cancel is in the list because it stops the car's ACC, not the steering, and it is the one a driver is most likely to press expecting openpilot to keep the lane. Gas keeps its softer `gasPressedOverride` path, which is an override rather than a disable, so steering continues through it too. Suppressing an event is narrower than changing what raises it: anything else upstream adds in the same event type still disengages. The one cost is `buttonCancel`'s `ET.NO_ENTRY`, so a cancel press no longer blocks a new engage — the same statement from the other side, and the driver's off switch is the LKAS button either way.
- **The enable rides the safety param, not `alternative_experience`.** `toyota_init` has to see it to pick its rx-check set, and the param reaches `init` by construction while alt-exp only happens to be set first by pandad. `ToyotaSafetyFlags.LATERAL_ENGAGE` is `16 << 8`, the next free Toyota flag, and a stock config's params and rx-check array are byte-identical to upstream's. Every armed brand has its own bit the same way — `GMSafetyFlags.LATERAL_ENGAGE`, `ChryslerSafetyFlags.LATERAL_ENGAGE`, one per mode header — and `moonpilot/tests/test_engage.py` reads those headers and fails if a row of `LATERAL_ENGAGE_FLAGS` drifts from the constant beside it, in either direction.

`moonpilot/engage.py` is the openpilot side, wired through four seams: `openpilot/selfdrive/car/card.py` calls `moonpilot_engage_safety_param()` before `CarParams` is written, `openpilot/selfdrive/controls/controlsd.py` builds `moonpilot_actuator_gate()` and puts both actuator permissions through it, `openpilot/selfdrive/selfdrived/selfdrived.py` runs `LateralEngage.update()` after every other event source and uses `controls_allowed()` for the panda cross-check, and `openpilot/selfdrive/pandad/pandad.cc` publishes the flag from the panda health bit `HEALTH_FLAG_CONTROLS_ALLOWED_LATERAL`. Eight things about it are not obvious:

- **Latching is what makes an authoritative disable last, and it is released on an edge.** With `pcmDisable` and `pedalPressed` suppressed, the events that would keep re-disengaging are gone, so an authoritative disable (`USER_DISABLE`, `IMMEDIATE_DISABLE`) latches the state off in the module and only a re-arm gesture clears it: the cruise main switch coming back on, the LKAS button, or ACC's **rising** edge — not ACC merely being set. Clearing on the level would undo a driver's LKAS press one frame later for anyone cruising with ACC set, which makes their own off switch look broken; `moonpilot/tests/test_engage.py` pins both directions. **The latch is not a palette state, but it is not silent either**: the border stays off — that reading is true, and a color would have to fight the palette for it — and what the driver gets instead is a permanent banner, `EventName.lateralEngageOff`, added by `LateralEngage.update` for every cycle `_blocked` is set and withdrawn the moment a re-arm clears it. It exists because the fork's own suppressors are what make the state silent in the first place: `pcmDisable` and `pedalPressed` are the events upstream would have explained a disengagement with, so a latched car looks exactly like a car with nothing switched on. It is deliberately **not** the broader "armed and not steering": a `NO_ENTRY` hold (a standstill with the brake, a model still loading) and a soft disable both already carry upstream's own alert and are states the driver can do nothing extra about, so the banner keys on the latch alone. That also covers the safety layer failing, which is the failure this feature cannot otherwise see — a panda that grants no lateral authority (an rx check that never settles, a `safetyConfigs` the seam never flagged, firmware without the health bit) raises `controlsMismatch`, an `IMMEDIATE_DISABLE`, so it lands *here*. There is no reason-specific text for it because there cannot be: the grant is cleared whenever openpilot is not engaged, so a latched car and an ungranted one are indistinguishable from outside. Two properties make it safe. It carries `ET.PERMANENT` and nothing else — no `USER_DISABLE`, `IMMEDIATE_DISABLE`, `SOFT_DISABLE`, `NO_ENTRY` or `ENABLE` — so the banner can never feed the latch that causes it, and it cannot raise the `NO_ENTRY` that would block the re-arm request. And it is debounced by upstream's own `creation_delay=1.0`, so the frame or two an engage takes, or a panda granting a frame late, cannot flash it. `ET.PERMANENT` is in `current_alert_types` for every state, so it surfaces while disabled — which is the only time it matters — and `Priority.LOWER` means a real alert outranks it, as the probe shows: `controlsMismatch`'s "TAKE CONTROL IMMEDIATELY" holds the banner off for the frames it is up.
- **A soft disable is deliberately not latched, and the request is gated on it instead.** `SOFT_DISABLE` is upstream's *recoverable* disable — `StateMachine` returns to `enabled` on its own once the condition clears inside `SOFT_DISABLE_TIME`, which is exactly what sunnypilot's MADS `paused` state exists for — so latching it would cost half-engagement for the rest of the drive on an EPS temp fault or a door that upstream rides out. Both halves of that fix are load-bearing: `SOFT_DISABLE` is out of the latch, and into the request's exclusion list (`not enabled and not blocked and not ENABLE and not NO_ENTRY and not SOFT_DISABLE`), because `bigModelFailed` is a `SOFT_DISABLE` upstream raises *without* a `NO_ENTRY` and would otherwise engage and soft-disable in a loop. Park and reverse are the fork's own exception instead: `wrongGear` carries both the `NO_ENTRY` refusal and a `SOFT_DISABLE` upstream would ride out for `SOFT_DISABLE_TIME` while the model's path kept being steered, so the fork adds `buttonCancel` below the latch check — steering stops on the frame the gear lands, the half-engagement is paused rather than ended, and D resumes it with no driver gesture — and reverse additionally has `reverseGear`'s permanent and user-disable alerts filtered. **Neutral is the other half of that exception**: the gear event is dropped outright while the car's own ACC is off, because steering without speed authority is meaningful with the drivetrain disconnected, so the half-engaged state may engage in neutral and stays engaged through a shift into it; set ACC — the full stack — and the event comes back, so the same quiet disengage ends it, at most one control cycle after `controlsAllowed` rises on an openpilot-longitudinal car whose ACC does engage in neutral. The one half of this no test here can reach is the car's: panda's rule has no gear check, so the fork now commands LKA torque in neutral, and whether the EPS applies it — or its lane-keeping ECU faults the way it does on a dropped frame stream — is a device fact, learned on a drive and not on this PC. Measured against upstream's state machine, old policy vs new: a 0.2 s `steerTempUnavailable` and a 5 s `doorOpen` both left it `disabled` forever and never re-asked, while the new one ends `enabled`; a fault that never clears still asks zero times in 9 s, so the loop is closed. Pinned by `test_a_soft_disable_is_not_latched`, `test_a_soft_disable_that_stays_does_not_nag` and `test_a_soft_disable_recovers_by_itself`.
- **The engage request is `buttonEnable`, under `not enabled and not blocked`.** `NO_ENTRY` is what keeps a standstill or an uncalibrated car from nagging with refuse alerts — the attempt simply repeats once the blocker clears — and the `not blocked` half is what stops the latch from being undone by the very next frame's arming request. Upstream's own `pcmEnable` on the same frame counts as the ask, so the fork does not stack a second enable event on it. Park and reverse emit one `buttonEnable` on entry, or on an LKAS re-arm, even though `wrongGear` is present, because StateMachine needs `ENABLE` plus `NO_ENTRY` to show the `Gear not D` refusal; `_wrong_gear_seen` prevents a retry on every frame the gear is held, and the cost it buys is a car booted in park with the main switch already on showing that refusal once at startup. Neutral takes no refusal at all while the car's ACC is off — the half-engaged state is allowed there — and only the full stack is blocked. The request is still feature-gated: with lateral engagement off or unavailable, the seam returns untouched upstream events.
- **One of upstream's disengages is inert here rather than suppressed**, and it is worth knowing before "fixing" the absence: `steerDisengage` rides the same Tesla-only `steering_disengage` signal the safety rule's override term does. Cancel used to be the other one, as a per-brand accident — Toyota's wheel emits no `ButtonType.cancel` at all while Honda's and Volkswagen's do — and is a suppression now, so all three brands take the same path instead of a coincidence of wiring.
- **The panda cross-check has to see the new permission**, or half-engaged reads as `controlsMismatch` and disengages. `LateralEngage.controls_allowed(ps)` accepts either flag; that keeps the mismatch check sharp instead of switching it off.
- **openpilot never offers the panda a frame it will refuse, and that is where the acceleration half of the feature lives.** A rejected frame is silent to the sender — the car simply never receives it — so `ActuatorGate` reads the panda's own grants back (`pandaStates.[].controlsAllowedLateral` and `controlsAllowed`) and the controlsd seam gates `CC.latActive` and `CC.longActive` on both of them beside upstream's expressions. It is built once, at construction, so the toggle keeps its documented restart, and it returns True on every car the feature is not enabled for, which is what keeps a stock config byte-identical. It closes two fork defects that the car itself found. Steering stops dying on the `desired_torque_last` reset above, because the command now waits for the grant instead of the grant for the command. And `CC.longActive` waits for `controlsAllowed`, so the half-engaged state commands no acceleration the safety layer would refuse: on an **openpilot-longitudinal Toyota** — `pcmCruise` is True there *and* `openpilotLongitudinalControl` is True, so the half-engaged state used to be longitudinal-active — the fork keeps sending `ACC_CONTROL` at `ACCEL_CMD=0`, the inactive value `longitudinal_accel_checks` accepts, where openpilot's refused frames were the PCM's only ACC stream: it went silent for ~1 s, the PCM set `ACC_FAULTED`, and that is an `IMMEDIATE_DISABLE`, hence "TAKE CONTROL IMMEDIATELY" and then a permanent "Cruise Fault". Half-engagement on such a car is therefore **steer-only** — the driver's foot owns speed until they set ACC, which is the grant that turns the longitudinal half back on. A `pandaStates` that is missing or stale makes the gate command nothing, which is the same direction the panda's own refusal takes.
- **The decision is made once, at construction**, like the fork's other behavior toggles, so the row takes a restart — which its description says.
- **A half-engaged car gets a color upstream had spent elsewhere, and that is `moonpilot/ui/onroad.py`'s whole job.** Upstream renders engagement as a palette keyed off `ui_state.status`, which is `selfdriveState.enabled` and nothing else: tizi's road-view border (`BORDER_COLORS`) and mici's lane lines (`LANE_LINE_COLORS`) each read disengaged / override / engaged. On a stock-ACC car that palette has always meant "openpilot steers and the ACC I set is holding speed", because openpilot never owns speed there — so half-engagement paints it with nobody holding speed, which is the one combination the car's visual grammar has no reading for, and the reading a driver is most likely to take from a lit-up car is that it is driving. Blue is the fork's answer, and the palette becomes one color per thing happening: **gray nothing on, blue steering without speed authority, green both** — blue taken from disengaged, which moves to a neutral gray (`0x3A3E40`, marked in `BORDER_COLORS`; it was `0x122839`, a dark navy). Leaving disengaged blue as well would have made the half-engaged state impossible to spot at a glance; a car doing nothing deserves the neutral reading and a car steering for you does not. Blue is painted only while **openpilot is the thing steering**, which is three conditions and no more. Something is on (`status != DISENGAGED` — not redundant with the grant below, because `selfdriveState` and `pandaStates` are separate messages, so for a frame or two after a disengage the last panda message still reports the grant). The safety layer is still granting lateral authority (`pandaStates.[].controlsAllowedLateral and not controlsAllowed` — the fork's own grant against stock ACC engagement, exact rather than inferred from `carState`, false on every car where the rule was never enabled). And **the driver is not steering** (`carState.steeringPressed`, which is what raises upstream's own `steerOverride`, so whatever makes a *fully* engaged car read as overridden makes a half-engaged car gray too; it cannot come from the safety layer, whose steering-override term is upstream's `steering_disengage`, set only by Tesla's rx hook). That last one is the whole point of the feature's honesty: blue would claim openpilot is steering while the driver's own hands are on the wheel doing the work. `gasPressedOverride` deliberately does **not** drop the color — in half-engagement the driver's foot owns the speed, so they are on the pedal much of the time and the car is steering for them throughout. Hence the predicate is not simply "status isn't OVERRIDE". For the frame where the driver's hands are on the wheel before `selfdriveState` has caught up, the fork returns the palette's own `OVERRIDE` color rather than `None`: deferring to upstream there would paint `ENGAGED` **green** on a car that is only steering, which is the reading the module exists to prevent, and in mici that same return is upstream's white lane color — each tree's own neutral, not a copy of it in fork code. Both call sites use the delegate shape (`... or BORDER_COLORS.get(status, ...)`), so upstream's expression stays on the line and `None` means it runs unchanged for every car that is not half-engaged — feature off, unavailable, or simply not one of the three brands. Deliberately **not** done by adding a fourth `UIStatus`: it is consumed as `== ENGAGED` or `.get(status, DISENGAGED)` in about eight places per tree, so a new value would paint mici's lane lines disengaged-black and tizi's border disengaged-gray while the car is steering. Only the two most salient channels are replaced — tizi's border, mici's lane lines; the DM arc, HUD `MAX` box, confidence ball, camera dim and wheel icon are left to upstream. `moonpilot/tests/test_onroad.py` pins the three conditions, the driver-steering neutral, the gas override and the fallback; the end-to-end values above were read from rendered frames of both trees.

The ceiling is the car, and after the two arming modes it is short: **every brand openpilot drives whose interface reports `CP.pcmCruise`**, not `passive`, and not `ToyotaFlags.UNSUPPORTED_DSU` (those read the main switch out of `DSU_CRUISE` at 5 Hz, below panda's 10 Hz rx-check minimum, and being switch-armed they have no second signal to fall back on). `CP.pcmCruise` is the flag the gate tests, and on Honda, Hyundai and Volkswagen it is `not openpilotLongitudinalControl`, while **on Toyota, and on every brand whose interface leaves it at upstream's default, it stays true under openpilot longitudinal control too** — so such a car is in scope and gets the steer-only half-engagement above, not an exclusion. A `pcmCruise` false car is out because the half-engaged state cannot exist there: openpilot owning acceleration means engaging it owns speed, which is the thing this feature is not. `LATERAL_ENGAGE_FLAGS` in `moonpilot/engage.py` is the brand table and the gate both, so the row a driver sees and the behavior they get cannot disagree; it names the safety-param bit per brand, and those bits are a wire contract with each brand's own mode header (`HONDA_PARAM_LATERAL_ENGAGE`, `TOYOTA_PARAM_LATERAL_ENGAGE`, `FLAG_VOLKSWAGEN_LATERAL_ENGAGE`). **What a brand needs to be listed is a free bit in its own safety-param space and one `lateral_engage_set_enabled(..., LATERAL_ENGAGE_ARM_HOST)` line in its safety init** — no CAN decode at all, which is the whole reason ARM_HOST exists. A brand that also has an already-rx-checked cruise main switch is armed on that instead (`LATERAL_ENGAGE_ARM_SWITCH`: Toyota, Honda, Volkswagen MQB/MEB) — Toyota's decode is the fork's, Honda's (`SCM_FEEDBACK` 0x326 @10 Hz, `SCM_BUTTONS` 0x1A6 @25 Hz) and Volkswagen's (`TSK_06` @50 Hz, `Motor_51` @50 Hz) are upstream's own — and that decode is the only part of this a car has to validate: a wrong rate does not degrade the feature, it clears `controls_allowed` (`safety.h`'s `frequency < 10U` and lagging paths). Volkswagen is two platforms short of its name: **PQ and MLB are excluded by flag**, because neither sets `acc_main_on` in the stock-ACC configuration this feature is for (PQ's is set only under openpilot longitudinal control, MLB's is not set at all). Honda needed one more thing no other brand did: **its steering permit is its own, not `lateral.h`'s**. Every other steering brand calls `steer_torque_cmd_checks` / `steer_angle_cmd_checks` / `steer_curvature_cmd_checks`, which carry the widened test; Honda's `tx_hook` tests `controls_allowed` directly, so that one line reads `(controls_allowed || controls_allowed_lateral)` too. Without it the feature would be enabled and still unable to steer. A brand that decodes a main switch but has no bit is the only thing left to add, and that is those two steps plus a `LateralEngageSafetyTest` subclass in that brand's test module. The re-arm gestures are brand-generic in the code: `ButtonType.lkas` (emitted by Toyota TSS2 and by Honda's SCM_BUTTONS LKAS setting button, and consumed by nothing in either tree), ACC's rising edge, and cycling the main switch, which works everywhere. **Volkswagen has no spare button at all** — every one of its buttons is an ACC function — so it relies on the latter two.
