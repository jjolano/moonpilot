# Plan-timed path steering
`moonpilot/curvature.py` time-shifts the decoded `modelV2.action.desiredCurvature` along the model's own path. The action remains the authoritative base; the two rows that add to it are `MoonpilotPathSmooth`'s lead and `MoonpilotPathLookahead`'s lead-in. The `controlsd` seam is `self.curvature_reference = moonpilot_curvature()`, a factory returning `None` when both rows are off, and its call remains between upstream's `new_desired_curvature` selection and `clip_curvature`. The choice is made once at construction, so the offroad-only rows take a restart.

- **The response horizon is `capture_age + lat_delay`.** `capture_age = now - model.timestampEof * 1e-9`, while `message_age = now - model_recv_time` independently measures how long the message sat after receipt. `controlsd` supplies its `selfdriveState` receive time as `now`, the `modelV2` receive time, and `lateralDelay + LAT_SMOOTH_SECONDS`; the fork reads `orientationRate.z` on the time grid published in `model.orientation.t`. On routes 413–418 the capture age was 35 / 60 / 81 ms (p5 / p50 / p95) at control time, so the freshness gate passed on every frame above 5 m/s.
- **The delay is the fork's estimate, learned down to 10 m/s, and applied under a cap.** Upstream `lagd` learned only above 50 mph and carried that one number to every speed: on an 810 s sub-50-mph route `lateralDelay` sat bit-identical at 0.220576, and routes 000003f3…0000040a show the mechanism — 28 cached blocks at a mean of 0.228 against ~0.40 s measured by the same estimator on those drives, because a highway block is rare and weighs 1/50. `moonpilot/lagd.py` now publishes `lateralDelay` with a 10 m/s gate, a 10-block ring and a cache that keeps its blocks; the per-band replay behind the gate read 0.39 / 0.36 / 0.40 s at 10–17 / 17–22 / above 22 m/s. Below 10 m/s too few windows pass the quality gates to say anything, so a parking-lot or intersection delay is still the cruising one. These are closed-loop numbers and they move with the controller in the wrong direction: the torque controller's feedback holds the wheel to the request from `lat_delay` ago, so the wheel's lag behind the request follows the applied delay (model→wheel cross-correlation above 10 m/s: 250 ms at 0.228 s on `00000408`, 425 ms at 0.37 s on `0000040e`, 480 ms at 0.42 s on `0000040d`), and the estimate reads that lag plus the vehicle's response — `0000040e`'s first partial block read 0.469 s at 0.32 applied. So the applied value is capped at `MOONPILOT_LAT_LAG_MAX_APPLIED` = 0.25 s while the blocks and `lateralDelayEstimate` stay uncapped and logged.
- **There is no re-sample of the action itself.** modeld already samples the plan at `lateralDelay + frame_delay + action_delay` (75 ms), so the former `MoonpilotPathPreview` correction — `clip(0.3 * (response_curvature - desiredCurvature), ±0.8 / v²)` — re-read nearly the same point: a frame-exact controlsd reconstruction of routes 413/414/417/418 matched the logged command to a median error of 0 and put the correction at 0.006–0.011 m/s² p99, with no measurable shift in the command's timing. It and its row were removed; without a smoothing lead or a look-ahead the reference is not built.
- **Freshness and shape failures are exact pass-throughs.** Both ages must be non-negative and no older than `2 * DT_MDL`; the model must be valid and alive; the request, speed, delay, clocks, yaw, yaw-rate, and both published time grids must be finite; the grids must be equal and strictly increasing; and the response horizon must be positive and inside the published trajectory. A stale, future-dated, malformed, slow-speed, or out-of-grid input returns `desiredCurvature` bit-for-bit, with no extrapolation or manufactured finite substitute. A valid `lateralManeuverPlan` bypasses the fork reference entirely because that override has no matching `modelV2` trajectory.
- **The reference holds no state.** Each frame's shift is computed from that frame's model and clock. Upstream's downstream `clip_curvature` still applies ISO lateral jerk, lateral-acceleration, and maximum-curvature limits, so the fork cannot widen the actuator envelope. A steady-radius path is unchanged because its planned curvature is the same at every horizon.
- **The torque controller does not count plan age twice.** Current-request feedforward still handles the live request; feedback uses the full plant delay while tightening and only the already-existing jerk lookahead while unwinding. The car interface's downstream torque-rate limit remains unchanged.
- The module remains `curvature.py`, not `path.py`, because `moonpilot/paths.py` owns storage roots. `moonpilot/tests/test_curvature.py` pins the factory's bindings, the ramp lead of exactly `slope * tau`, the filter settling on the unfiltered ramp once led, the lateral-acceleration bound, and every freshness/shape pass-through against fixtures that are corrected when fresh.
- **`MoonpilotPathSmooth` is an opt-in stage on the request, led by its own time constant.** `moonpilot_path_smooth()` is the sibling factory (`self.moonpilot_path_smooth` in controlsd), off by default and chosen at construction, so its row takes a restart; when it returns `None` controlsd applies nothing. The param is an INT index into `PATH_SMOOTH.choices` — off, 0.05, 0.10 or 0.15 s, the same order as `MOONPILOT_SMOOTH_TAUS` — rendered as a choice row (tizi `multiple_button_item`, mici `BigMultiParamToggle`), and an out-of-range value reads as off. When on it is a first-order IIR at the control rate (`x += (1 - exp(-dt/tau)) * (u - x)`) between the reference and `clip_curvature`, and it holds one piece of state: while not steering it tracks the input, so a re-engage starts from the curvature the car is already on and never re-injects pre-disengage state, and a non-finite request passes through with the state held. `moonpilot_curvature()` binds the same τ as the reference's `lead`: `(yaw_rate(horizon + τ) - yaw_rate(horizon)) / v`, clipped to ±0.8 m/s², added in full before the filter. A first-order filter lags a ramp by τ and the planned curvature of a ramp is linear on the grid, so on a ramp the filtered command settles on the unfiltered one. τ is **not** in the torque controller's `lat_delay`: the controller buffers the already-filtered request, so folding τ into its setpoint delay held the wheel back a second time (on `0000040d` at 0.10 s and `0000040e` at 0.05 s the filter delayed the request by 60 and 30 ms, while each τ also lengthened the setpoint delay). Until this lead, the τ instead lengthened the 0.3-gain re-sample's horizon, which recovered about 3 ms: on 418 (0.05 s) the command trailed the action by 30 ms on all 7 steering runs. A free-running replay of the request chain over 413/414/417/418 (29 runs above 5 m/s, lag = cross-correlation peak against the unfiltered action, interpolated):

  | τ | lag, no lead | lag, lead τ | step RMS (unfiltered 8.5 mm/s² per frame) | rms deviation from the action, no lead → lead |
  |---|---|---|---|---|
  | 0.05 s | 34 ms | 18 ms | 3.8 → 4.0 | 21.5 → 19.5 mm/s² |
  | 0.10 s | 75 ms | 25 ms | 3.1 → 3.2 | 32.8 → 25.8 mm/s² |
  | 0.15 s | 117 ms | 26 ms | 2.7 → 2.9 | 43.7 → 31.5 mm/s² |

  The remaining lag is the model re-planning faster than its own path predicts. Scaling the lead past τ chased it down (1.5–2 × τ reached ~0–11 ms) but tracked the action worse at every scale tried — rms deviation 20.5–26.2 / 28.1–40.4 / 34.7–52.4 mm/s², all above lead τ's and at 2 × τ above the unled filter's — and at 0.10–0.15 s its lag spread went negative by tens of ms, so the lead stays at τ. Below 5 m/s the reference passes through and the filter lags by its full τ. On `00000408--9c6c861389` (filter applied to the logged request, wheel response held as recorded), the P-term's per-frame step RMS at <3 / 3–9 / ≥9 m/s fell from 169 / 65 / 13 CAN units to 68 / 33 / 7 at 0.05 s, 52 / 27 / 6 at 0.10 s and 49 / 25 / 6 at 0.15 s — most of the benefit by 0.10 s. `TestSmoothFactory`, `TestPathSmooth` and `TestSmoothingLead` pin it.

## Continuous torque friction compensation

`moonpilot/latcontrol.py` logs controller version **1001** for the continuous friction map. Version 1000's compensation switched from zero to a nonzero value at 0.10 m/s² and dropped back to zero at 0.05 m/s². With the latest analyzed route's learned coefficient, those transitions added about 104 and removed about 52 CAN torque units.

The replacement retains the near-zero quiet region without a release latch:

- Input is still `error + MOONPILOT_JERK_GAIN * desired_jerk`, with the gain unchanged at 0.3.
- The quiet band is `max(car_deadzone, MOONPILOT_FRICTION_DEADBAND)`, with the fork deadband at 0.05 m/s² and the car's steering-angle deadzone converted to acceleration as before.
- Subtract that band from the input's magnitude, retaining its sign, then pass the result through the existing `get_friction` helper with a 0.15 m/s² ramp. Compensation is zero at the band's edge and reaches the unchanged learned maximum at `quiet_band + 0.15`; with a zero car deadzone it still reaches full compensation at 0.20 m/s².
- There is no friction state to carry across an error reversal or reset, no new filter lag, and no change to the measurement filter, request delay, PI gains, Toyota torque/rate limits, or safety layer.

An 84,708-frame replay of `000003fe--2ed5f82220`, using its original timestamps and recorded plant inputs, reduced the median friction-term step at the old release events from 0.0748 to 0.0225 normalized torque. The old controller's replay matched logged requests with a 99th-percentile absolute error of 0.0020. This is command-path evidence, not a closed-loop prediction: smaller corrections can occur more often, and physical steering stiction or EPS deadband may remain. A new drive must check notch size, tracking error, and rough-road weaving before changing jerk gain or shrinking the quiet band.
