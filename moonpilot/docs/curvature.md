# Response-aligned path steering
`moonpilot/curvature.py` aligns the model's path with when steering is expected to respond. The decoded `modelV2.action.desiredCurvature` remains the authoritative base for every action contract; `MoonpilotPathPreview` adds only a bounded correction toward the path. The `controlsd` seam is `self.curvature_reference = moonpilot_curvature()`, a factory returning `None` when the toggle is off, and its call remains between upstream's `new_desired_curvature` selection and `clip_curvature`. The choice is made once at construction, so the offroad-only row takes a restart.

- **The response horizon is `capture_age + lat_delay`.** `capture_age = now - model.timestampEof * 1e-9`, while `message_age = now - model_recv_time` independently measures how long the message sat after receipt. `controlsd` supplies its `selfdriveState` receive time as `now`, the `modelV2` receive time, and `lateralDelay + LAT_SMOOTH_SECONDS`; the fork samples `orientation.z` and `orientationRate.z` through upstream's `get_curvature_from_plan` on the time grid published in `model.orientation.t`.
- **The delay is the fork's estimate, learned down to 10 m/s, and applied under a cap.** Upstream `lagd` learned only above 50 mph and carried that one number to every speed: on an 810 s sub-50-mph route `lateralDelay` sat bit-identical at 0.220576, and routes 000003f3…0000040a show the mechanism — 28 cached blocks at a mean of 0.228 against ~0.40 s measured by the same estimator on those drives, because a highway block is rare and weighs 1/50. `moonpilot/lagd.py` now publishes `lateralDelay` with a 10 m/s gate, a 10-block ring and a cache that keeps its blocks; the per-band replay behind the gate read 0.39 / 0.36 / 0.40 s at 10–17 / 17–22 / above 22 m/s. Below 10 m/s too few windows pass the quality gates to say anything, so a parking-lot or intersection delay is still the cruising one. These are closed-loop numbers and they move with the controller in the wrong direction: the torque controller's feedback holds the wheel to the request from `lat_delay` ago, so the wheel's lag behind the request follows the applied delay (model→wheel cross-correlation above 10 m/s: 250 ms at 0.228 s on `00000408`, 425 ms at 0.37 s on `0000040e`, 480 ms at 0.42 s on `0000040d`), and the estimate reads that lag plus the vehicle's response — `0000040e`'s first partial block read 0.469 s at 0.32 applied. So the applied value is capped at `MOONPILOT_LAT_LAG_MAX_APPLIED` = 0.25 s while the blocks and `lateralDelayEstimate` stay uncapped and logged.
- **The action stays the anchor.** The correction is `clip(0.3 * (response_curvature - desiredCurvature), ±0.8 / max(v_ego, MIN_SPEED)²)`, so a gain of zero is upstream exactly, an action head that differs from the path is pulled toward rather than replaced by it, and the bound remains a fixed lateral acceleration at every speed; a full-route exact recompute (16,072 ticks) puts |correction| at max 6.0e-3 m/s², 0.76% of authority, so the raw divergence — not the authority — is the binding constraint.
- **Freshness and shape failures are exact pass-throughs.** Both ages must be non-negative and no older than `2 * DT_MDL`; the model must be valid and alive; the request, speed, delay, clocks, yaw, yaw-rate, and both published time grids must be finite; the grids must be equal and strictly increasing; and the response horizon must be positive and inside the published trajectory. A stale, future-dated, malformed, slow-speed, or out-of-grid input returns `desiredCurvature` bit-for-bit, with no extrapolation or manufactured finite substitute. A valid `lateralManeuverPlan` bypasses the fork reference entirely because that override has no matching `modelV2` trajectory.
- **The correction itself holds no second smoothing state.** The full bounded correction is available on the first control frame and advances with the live model age. Upstream's downstream `clip_curvature` still applies ISO lateral jerk, lateral-acceleration, and maximum-curvature limits, so the fork cannot widen the actuator envelope. A steady-radius path remains unchanged because `get_curvature_from_plan` reads the same curvature at every horizon.
- **The torque controller does not count plan age twice.** Current-request feedforward still handles the live request; feedback uses the full plant delay while tightening and only the already-existing jerk lookahead while unwinding. The response-aligned reference accounts for plan age once, and the car interface's downstream torque-rate limit remains unchanged.
- The module remains `curvature.py`, not `path.py`, because `moonpilot/paths.py` owns storage roots. `moonpilot/tests/test_curvature.py` pins the 80 ms capture plus 200 ms delay as a 280 ms sample, live 10 ms advancement, action anchoring, the lateral-acceleration bound, immediate first-call behavior, and every freshness/shape pass-through.
- **`MoonpilotPathSmooth` is an opt-in stage on the request, not on the correction above.** `moonpilot_path_smooth()` is the sibling factory (`self.moonpilot_path_smooth` in controlsd), off by default and chosen at construction, so its row takes a restart; when it returns `None` controlsd applies nothing and the frame is stock-exact. The param is an INT index into `PATH_SMOOTH.choices` — off, 0.05, 0.10 or 0.15 s, the same order as `MOONPILOT_SMOOTH_TAUS` — rendered as a choice row (tizi `multiple_button_item`, mici `BigMultiParamToggle`), and an out-of-range value reads as off. When on it is a first-order IIR at the control rate (`x += (1 - exp(-dt/tau)) * (u - x)`) between the fork's correction and `clip_curvature`, and it holds one piece of state: while not steering it tracks the input, so a re-engage starts from the curvature the car is already on and never re-injects pre-disengage state, and a non-finite request passes through with the state held. Its τ lengthens the response horizon above and **not** the torque controller's `lat_delay`: the controller buffers the already-filtered request, so the filter's lag is already in it, and folding τ into its setpoint delay as well held the wheel back a second time — on `0000040d` (0.10 s) and `0000040e` (0.05 s) the filter itself delayed the request by 60 and 30 ms (model→controller cross-correlation), while each τ also lengthened the controller's setpoint delay. The intended effect, from an offline replay of this route's engaged frames: about half the large controller-output steps and about 45% of total step energy, for ~0.15 s of added path lag (≈2 cm of lateral error at typical speeds), with sharp-cornering targets unchanged because geometry, not chatter, drives those. On `00000408--9c6c861389` (filter applied to the logged request, wheel response held as recorded), the P-term's per-frame step RMS at <3 / 3–9 / ≥9 m/s fell from 169 / 65 / 13 CAN units to 68 / 33 / 7 at 0.05 s, 52 / 27 / 6 at 0.10 s and 49 / 25 / 6 at 0.15 s — most of the benefit by 0.10 s; the preview correction does not act below 5 m/s, so there the lag is uncompensated. `TestSmoothFactory` and `TestPathSmooth` pin it.

## Continuous torque friction compensation

`moonpilot/latcontrol.py` logs controller version **1001** for the continuous friction map. Version 1000's compensation switched from zero to a nonzero value at 0.10 m/s² and dropped back to zero at 0.05 m/s². With the latest analyzed route's learned coefficient, those transitions added about 104 and removed about 52 CAN torque units.

The replacement retains the near-zero quiet region without a release latch:

- Input is still `error + MOONPILOT_JERK_GAIN * desired_jerk`, with the gain unchanged at 0.3.
- The quiet band is `max(car_deadzone, MOONPILOT_FRICTION_DEADBAND)`, with the fork deadband at 0.05 m/s² and the car's steering-angle deadzone converted to acceleration as before.
- Subtract that band from the input's magnitude, retaining its sign, then pass the result through the existing `get_friction` helper with a 0.15 m/s² ramp. Compensation is zero at the band's edge and reaches the unchanged learned maximum at `quiet_band + 0.15`; with a zero car deadzone it still reaches full compensation at 0.20 m/s².
- There is no friction state to carry across an error reversal or reset, no new filter lag, and no change to the measurement filter, request delay, PI gains, Toyota torque/rate limits, or safety layer.

An 84,708-frame replay of `000003fe--2ed5f82220`, using its original timestamps and recorded plant inputs, reduced the median friction-term step at the old release events from 0.0748 to 0.0225 normalized torque. The old controller's replay matched logged requests with a 99th-percentile absolute error of 0.0020. This is command-path evidence, not a closed-loop prediction: smaller corrections can occur more often, and physical steering stiction or EPS deadband may remain. A new drive must check notch size, tracking error, and rough-road weaving before changing jerk gain or shrinking the quiet band.
